# Production deployment

The backend runs on Render and uses the existing Supabase PostgreSQL database.
The frontend runs on Vercel. No deployment step creates, clears, or resets a
Supabase database.

## 1. Supabase PostgreSQL

1. In Supabase, open the existing project and use **Connect** to copy the
   PostgreSQL connection string suitable for your deployment environment.
2. Add `sslmode=require` if it is not already present.
3. Do not paste the value into source control. Add it only as Render's
   `DATABASE_URL` environment variable. The application rejects missing or
   non-PostgreSQL URLs when `DEBUG=False`; SQLite is local-development-only.
4. The first Render deployment runs Django migrations against that existing
   database. Review the migration plan in a safe environment before a first
   production deploy:

   ```bash
   python manage.py showmigrations
   python manage.py migrate --plan
   ```

   `migrate --plan` is read-only. Do not use `flush`, `reset_db`, or migration
   rollbacks against production.

## 2. Render: Django API

Create a Render Blueprint from this repository. The included `render.yaml`
uses `backend/` as its root directory, installs dependencies, collects static
files, runs migrations in Render's pre-deploy step, and starts Gunicorn. The
pre-deploy migration command does not run until you choose to deploy; it uses
only the existing Supabase database configured by `DATABASE_URL`.

Set these Render environment variables:

| Variable | Value |
|---|---|
| `SECRET_KEY` | Generated by Render or a new private random value |
| `DEBUG` | `False` |
| `DATABASE_URL` | Existing Supabase PostgreSQL URL, with SSL required |
| `ALLOWED_HOSTS` | The Render API host, for example `api.example.onrender.com` |
| `CORS_ALLOWED_ORIGINS` | The Vercel production origin, for example `https://app.example.vercel.app` |
| `CSRF_TRUSTED_ORIGINS` | The Render and Vercel HTTPS origins, comma separated |
| `OPENROUTER_API_KEY_1` … `OPENROUTER_API_KEY_5` | Optional server-only OpenRouter keys |
| `OPENROUTER_MODEL` | Optional OpenRouter model; defaults to `openai/gpt-oss-20b` |
| `JUDGE0_*`, `PISTON_BASE_URL`, `WANDBOX_BASE_URL` | Optional execution-provider settings |
| `SUPABASE_URL` | Supabase project URL used to verify Google OAuth access tokens |
| `SUPABASE_PUBLISHABLE_KEY` | Supabase publishable/anon key used only to verify a user token with Supabase Auth |

Before the first production deploy, set all required values, then review the
read-only migration plan against the existing Supabase database. Do not deploy
until the plan is acceptable:

```bash
python manage.py migrate --plan
```

Never add a `DATABASE_URL`, API key, or production secret to `.env.example`,
the repository, Vercel, or client-side `VITE_*` variables.

## 3. Vercel: React frontend

1. Import the repository in Vercel and set **Root Directory** to `frontend`.
2. Vercel detects Vite. Use `npm run build` and the default `dist` output.
3. Add this production environment variable, then redeploy:

   ```text
   VITE_API_URL=https://<render-api-host>/api
   ```

`VITE_API_URL` is public because Vite embeds it in the browser bundle. It must
contain only the backend API URL, never a database URL or a secret.

For Google OAuth, add these public Vercel variables:

```text
VITE_SUPABASE_URL=https://<your-project-ref>.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=<your-supabase-publishable-or-anon-key>
```

In Supabase **Authentication → URL Configuration**, set the production Site
URL and add `https://<your-vercel-domain>/auth/callback` to Redirect URLs.
For local development also add `http://localhost:5173/auth/callback` (or the
actual Vite origin). In **Authentication → Providers → Google**, keep Google
enabled with the Google OAuth client ID and client secret configured there.
In Google Cloud, add Supabase's callback URL shown by that provider page to
the OAuth client's **Authorized redirect URIs**. Do not use the frontend
callback as a Google Cloud redirect URI.

The Google client secret and every Supabase service-role key must remain out
of source control, Django, and Vercel. `SUPABASE_PUBLISHABLE_KEY` and
`VITE_SUPABASE_PUBLISHABLE_KEY` must contain the same public key; the former
lets Django call Supabase Auth's user endpoint to validate a user-provided
access token, while the latter is embedded in the browser bundle.

`frontend/vercel.json` rewrites browser routes to `index.html`, allowing React
Router URLs to work on refresh.

## 4. Post-deploy verification

1. On Render, run `python manage.py check --deploy` with production variables.
2. Confirm `python manage.py showmigrations` shows all migrations applied.
3. Visit the Vercel site, log in, and verify an authenticated API request.
4. Confirm requests from any origin other than the configured Vercel origin
   are rejected by CORS.
5. Confirm Render logs show PostgreSQL as the database engine; SQLite must not
   be used when `DEBUG=False`.
